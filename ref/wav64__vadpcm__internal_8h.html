struct wav64_state_vadpcm_t

WAV64 VADPCM decoding state (for a single mixer channel)

Notice that the state is accessed in part by RSP (state[2]) and in part by the CPU (bitpos) so we need to avoid false-sharing of cachelines. This is why we force a 16-byte alignment, so that it spans exactly 2 cachelines.

◆ VADPCM_GROUP_OFFSET

#define VADPCM_GROUP_OFFSET (   bits,
  j 
)    (((j) * (bits)) >> 1)

Bitstream layout of a VADPCM frame.

A frame always codes 16 samples and starts with one control byte (scaling << 4 | predictor), followed by the 16 residuals packed at wav64_header_vadpcm_t::residual_bits bits each, most significant bit first: 

residual i occupies payload bits [i*bits, i*bits + bits)

where payload bit 0 is the most significant bit of payload byte 0. For the classic 4-bit encoding this is exactly the usual nibble packing (residual i in nibble i), so 4-bit frames are bit-for-bit unchanged; 3-bit and 2-bit frames shrink the payload to 6 and 4 bytes respectively.

The mixer ucode reads the payload as four halfwords, one per group of four consecutive residuals: group j lives entirely inside the halfword starting at payload byte VADPCM_GROUP_OFFSET, which is why the packing has to be dense and MSB-first.

◆ WAV64_VADPCM_FILE_FRAMES

#define WAV64_VADPCM_FILE_FRAMES (   len)    (DIVIDE_CEIL(len, 32) * 2)

Frames actually stored in the file for a waveform of len samples.

audioconv64 pads the waveform to a multiple of 32 samples before encoding, but writes the unpadded length in the header, so the file always holds a few frames more than WAV64_VADPCM_FRAMES. The padding is part of the block-planar layout of stereo files, so it must be accounted for when addressing frames in the file.
